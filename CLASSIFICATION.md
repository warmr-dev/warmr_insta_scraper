# Классификация фото-сторис

Как работает AI-часть и что она показала на реальных данных.

Все цифры ниже — с одного живого прогона: 28 отслеживаемых аккаунтов, 151 сторис,
модель `gemini-flash-lite-latest`.

---

## 1. Что вообще доходит до AI

```
151 сторис в трее
├── 106 видео  → skipped_video, до AI НЕ доходят (§1)
└──  45 фото   → анализ
```

**Видео — 70% всех сторис.** Они отсекаются в фетчере, ещё до скачивания и до любого
обращения к модели, поэтому не стоят ничего. До классификатора доходит лишь 30%
найденного — это главный рычаг экономии, и он уже работает.

---

## 2. Результаты на 45 фото

| Оценка | Сторис | Что это |
|---|---|---|
| **8** | 2 | лиды — заявки на услуги |
| 1 | 5 | коммерческие, но не заявки |
| 0 | 38 | обычные личные сторис |

**Доля лидов: 2 из 45 (4.4%)**, то есть ~1.3% от всех найденных сторис.

Тридцать восемь нулей — это правильный ответ, а не сбой. Большинство сторис не
содержат никаких заявок, и классификатор их не выдумывает.

### Найденные лиды

```
@astana.hub   8/10   software development   гео: Astana
@astana.hub   8/10   software development   гео: Astana
```

Обе получили `accept` и **пропустили умную модель** (оценка ≥ 7), как требует §7.4 —
на них потрачен только дешёвый вызов.

## 3. Категории — сигнал считывается даже у отклонённых

| Категория | Сторис |
|---|---|
| (не определена) | 31 |
| florist | 7 |
| software development | 2 |
| floral design / delivery / arrangement | 3 |
| catering and restaurant | 1 |
| hookah lounge | 1 |

Показательно: у `@flowers.almaty` уверенно определена категория `florist`, гео у
`@dym_vostoka_almaty` — `Достык, 46`. Но оценки 0–1, потому что это **реклама своих
услуг**, а не поиск подрядчика. Именно это различие ловит поле
`is_offering_services`, и модель его отрабатывает верно.

Иными словами: контекст извлекается почти всегда, а высокая оценка ставится только
при реальном намерении заказать.

## 4. Маршрутизация и стоимость

Порог из §7.4:

- **0–4** → отказ, умная модель не вызывается
- **5–6** → уточняет умная модель
- **7+** → умную модель **пропускаем**, берём оценку дешёвой

На этой выборке в диапазон 5–6 не попало ничего, поэтому умная модель не
вызывалась ни разу. Все 45 фото обошлись одним дешёвым вызовом каждое.

**Расход: $0.0254 на 115 вызовов** — примерно **$0.0006 за фото**.

Грубая экстраполяция (осторожно, выборка мала): при 57 000 целей и такой же доле
фото стоимость анализа — десятки долларов в месяц, то есть в бюджет $650
укладывается с большим запасом. Настоящие цифры даст пилот на реальном объёме.

## 5. Повторно ничего не оплачивается

Критерий «уже платили» — наличие строки в `story_analysis`, а **не** в `stories`.
Это важно: сторис попадает в `stories` при первом же обнаружении в трее, задолго до
того, как её увидит AI.

Второй запуск:

```
уже анализировали ранее: 45 | новых к анализу: 0
Новых фото нет - все уже проходили через AI. Платить второй раз не за что.
```

Ноль вызовов, ноль скачиваний. Без этого при опросе раз в 2 минуты одна сторис
оплачивалась бы ~720 раз за сутки своей жизни.

## 6. Что модель возвращает по каждой сторис

Дешёвая модель отдаёт строгий JSON (проверяется Pydantic):

```json
{
  "score": 8,
  "explicit_purchase_intent": true,
  "seeking_contractor": true,
  "allowed_category": true,
  "is_spam": false,
  "is_offering_services": false,
  "asking_for_free": false,
  "complaint_only": false,
  "service_category": "software development",
  "geography": "Astana",
  "email_visible": null
}
```

Всё это сохраняется в `story_analysis.cheap_result` — при смене порогов старые
сторис можно переоценить без повторных вызовов модели.

При невалидном JSON — **одна** повторная попытка с требованием «только JSON», затем
сторис помечается `failed`. Гадать по некорректному ответу нельзя (§7.4).

## 7. Как посмотреть результаты

```bash
# распределение оценок
psql -d stories_monitor -c "select final_score, count(*) from story_analysis group by 1 order by 1 desc;"

# лиды
psql -d stories_monitor -c "select t.username, a.final_score, a.service_category
  from story_analysis a join stories s on s.story_id=a.story_id
  join targets t on t.user_id=s.target_user_id
  where a.final_score >= 7 order by a.final_score desc;"

# категории
psql -d stories_monitor -c "select coalesce(service_category,'(нет)'), count(*)
  from story_analysis group by 1 order by 2 desc;"

# расход
psql -d stories_monitor -c "select metric, round(sum(value)::numeric,4)
  from metric_samples where metric like 'ai_%' group by 1;"
```

Запуск — см. `HOWTO.md`, раздел 7b.

## 8. Оговорки

**Выборка мала.** 45 фото с 28 аккаунтов — этого мало для выводов о точности. Нужен
пилот из §Phase 6 спеки: 3–7 дней, 200–500 целей.

**Аккаунты нерелевантные.** Подписки тестового аккаунта — знакомые и локальные
заведения Алматы, а не целевая аудитория проекта. На настоящем списке целей доля
лидов будет другой.

**Точность не измерена.** Мы видим, что модель ставит осмысленные оценки, но никто
не размечал эти 45 фото вручную. Без эталона нельзя сказать, сколько заявок она
пропустила. Это нужно сделать на пилоте.

**OCR не работал.** `OCR_ENGINE=vision` откатился на `null` — модель читала картинки
напрямую, без отдельного текстового слоя. Сравнить tesseract и vision по цене
(как просит §7.4) ещё предстоит.
